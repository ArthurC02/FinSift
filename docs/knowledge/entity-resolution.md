# 機構解析

「這份文件是哪一家的？這張表是哪一家的？」——從資料夾、從財報封面、從法說會投影片的一角。

跨 `financialReports.entities`、`earningsCalls.matching`、`financialReports.profitability`、`regulatorDatasets`。

> 可信度：**程式碼 > 緊鄰常數的註解 > 這份文件**。`tools/knowledge_links.py` 只保證章節還在，不保證內容還對。

---

## 為什麼機構資料集中在一張表

`BANK_PROFILES` 之前是五張各自獨立的表（`BANKS`、`BANK_NAME_ALIASES`、`SUMMARY_CODE_OVERRIDES`、`SUMMARY_CODE_OVERRIDES_FINSUM`、`COMPOSITE_TERMS`）外加 `earningsCalls` 的 `PRIMARY_BANK_ENTITIES`——**加一家機構要改六個地方，而且沒有任何東西檢查六個都改了**。

漏改的下場不是報錯：少一筆 `composites` 只會讓某一家的輸出多出一列 N/A，跟「這家真的沒揭露」完全無法分辨。

現在那六個名字全部還在，只是改成從 profiles 推導出來的視圖；`_validate_profiles()` 在 import 時就擋下不完整的 profile，把執行期的靜默 N/A 變成啟動期的錯誤。

## profile 的六個欄位

`code_overrides` / `code_overrides_finsum` / `composites` 三個欄位屬於代碼問題，寫在 [科目代碼](account-codes.md)。以下三個是機構問題。

### industries

這家的財報寫在哪些準則下。**這是讓機構軸能安全開放的關鍵。**

別名必須是短名（法說會封面寫「玉山金控」，不會寫登記全名），而短名在同一個集團內會互撞：「國泰人壽保險股份有限公司」包含「國泰」，所以壽險的財報曾被解析成它的兄弟**銀行**，並套用了那家銀行的 overrides 與 composites。

把偵測範圍限縮到財報自己的產業，是用結構消除這個問題，而不是祈禱別名永遠不撞。銀行與金控兩種準則對每家都列，是因為兩種文件都在範圍內。

法說會簡報**沒有**登記全名，因此判不出產業。這時所有機構都保持候選——在那裡收窄會直接讓法說會偵測失效。

### aliases

全名／別名。兩個用途：把使用者輸入的 `--bank 台北富邦銀行` 正規化成 `北富銀`，以及在沒給 `--bank` 時從財報自己的文字偵測機構。「臺」「台」都要列，兩種寫法都出現過。

**別名不能是日常用語。**「第一」單獨當別名會命中每一家財報裡的「第一季」「第一階段」，使 `第一銀行` 在**所有**資料夾都成為候選，`detect_bank` 因歧義而全部拒絕——症狀是整批資料夾被靜默跳過，不是報錯。所以只收 `第一商業銀行` / `第一銀行` / `第一金`。

反方向也有一例：`北富銀` 收了單獨的「富邦」，因為 4Q25 法說會封面只寫「富邦金控」，不寫子行名。其他 profile 都不含「富邦」，所以不產生歧義——這是逐案確認過的，不是通則。

### primary_entities

每份法說會簡報**主體銀行**的名稱。

金控的簡報會同時報告其他子行（富邦華一銀行用人民幣、富邦銀行(香港)用港幣…），而這些表的列標籤一模一樣（存放比、總放款、營業費用）。`_BANK_LABEL_HINT` 分不出來，因為它們全都含「銀行」。

**抓錯子行比抓不到更糟。** 真實案例：一份富邦簡報產出了 存放比 72.17%、放款餘額 81,769——那是大陸子行人民幣表的數字，不是台北富邦銀行的。

英文／羅馬拼音要一起列，因為簡報附錄常用英文表頭（"E.SUN Bank's Income Statement"）。少了它，這種標題會命中 `_ENTITY_NAME_RE`（因為有 "Bank"）但命不中 primary alias，於是這家自己的附錄反而被當成別家的而拒絕。

**後來新增的六家（兆豐／台新／新光／永豐／第一／華南）的 `primary_entities` 沒有對過任何一份真實法說會簡報**——這六家是從 114Q4 個體財報加進來的，還沒有簡報跑過這個工具。它們只影響法說會擷取；要信任這六家的法說會輸出前，先拿真實簡報驗一次。

## 為什麼歧義要拒絕而不是取第一個

`detect_bank` 以前回傳 `BANK_NAME_ALIASES` 順序的第一個命中。那只有在「沒有任何一份財報會提到兩家」時才安全，而這個假設撐不過完整的台灣銀行清單：

- 別名一定是短名（法說會封面只寫「玉山金控」，`detect_industry_category` 那套登記全名的作法在這裡借不來）。
- 短名彼此互為子字串。
- 財報在關係人交易或同業往來附註裡提到同業，是常態而不是例外。

在這些條件下，first-match-wins 不會退化成 N/A——它會**靜默挑錯一家**，套用那家的 `COMPOSITE_TERMS` 與 `SUMMARY_CODE_OVERRIDES`，然後產出一整組看起來很合理的錯數字。

所以歧義一律拒絕。呼叫端本來就有「判不出來」的路徑（`statements` 要求 `--bank`，`cli` 跳過並說明），不需要新的控制流程，只需要一個能分辨兩種原因的訊息——那就是 `bank_candidates` 被公開出來的理由。

`bank_detection_message` 分三種而不是兩種：沒命中、多家命中、以及**產業本身沒有任何機構支援**。第三種給 `--bank` 也沒用（每個接受的值都會再被 layout 檢查擋掉），講成「無法自動偵測」會把人帶進死路。

## 法說會表格的機構分層

`entity_tier` 給三級：2 = 這份簡報的主體銀行、1 = 沒有標明機構的通用表、0 = 別家。**0 是直接跳過，不是排序排後面**——那些表的列標籤跟主體銀行一模一樣（存放比、總放款、營業費用），但數字是別家公司的，常常還是別的幣別。

`primary_aliases` 為 None（機構未知）時退回舊的 `_BANK_LABEL_HINT` 行為，而不是全部拒絕。

## 為什麼是白名單而不是黑名單

`_ENTITY_NAME_RE` 列的是「公司類型」字樣（銀行／金控／人壽／Bank／FHC…），而不是列出通用軸標籤（項目／期間／年度…）當黑名單。

黑名單會把任何沒列到的通用標籤**當成公司名**。真實案例：一份國泰簡報的 `| Quarterly | 4Q22 | ... |`，"Quarterly" 被讀成一個叫這名字的機構，然後被另一張真正掛銀行名的表在排序上壓過去——結果 NIM 解析到年度 FY25 的數字，而正確的 4Q25 就在那張被判為「Quarterly 公司」的表裡。

同樣的字彙在 `profitability._ENTITY_HEADING_NAME_RE` 又重複了一次。兩份都該住進 `core/`，但那是重構，當時那支 commit 是 bug fix——記在 `docs/TEST_DESIGN.md` §7。

## 獲利能力表的機構列

`_ENTITY_ROW_RE` 的「公司關鍵字」分支是**錨定**的（`$` 結尾）：`存放銀行同業` 這種普通科目名含「銀行」但後面還有字，曾被讀成機構列，把下面幾列全部當成它的續行吞掉。

前三個選項（合併／本公司／國泰）刻意保持**前綴**比對，這樣「本公司及子公司」還能運作。把那三個也錨定會用一個 false positive 換一個 false negative，而後者壞的是主要路徑。

編號標題（`1. 玉山金控及子公司`）也要過同一關：`_ENTITY_HEADING_RE` 會匹配**任何**編號行，所以第一頁的「1. 前言」曾讓整個檔案的 layout-3 表全部看起來像 layout-2 的，然後被整批跳過。

## 金管會名稱對照為什麼只有四家

`_GOV_BANK_NAMES` 把本專案的短名對到金管會試算表**自己那一欄印的字串**。

**刻意沒有擴充到後來加進 `BANK_PROFILES` 的六家。** 這個 key 必須是金管會試算表自己印的字串，不一定等於財報上的登記名稱，而且不讀一份真實的主管機關檔案就無法確認——這個 repo 又不能連 `banking.gov.tw` 去查（AGENTS.md 紅線第二條）。

猜「兆豐國際商業銀行」而錯一個字，看起來會跟「那個月金管會沒公布這家」完全一樣。所以沒對照到的機構是**拒絕**而不是猜，而且 `gov_name_note` 會說出是哪一種原因——「這家從來沒被對照過」跟「資料集連不上」是兩個不同的問題，修法也不同。
