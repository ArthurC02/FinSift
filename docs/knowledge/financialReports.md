# financialReports — 知識

財報側的背景知識。**規則本身留在程式碼裡**（門檻值旁的一行、`不要 X` 的祈使句）；這裡放的是「為什麼是這樣」的來龍去脈——實際踩過的坑、比對過的財報、試過而放棄的作法。

> 讀這份之前先讀 [AGENTS.md](../../AGENTS.md) 的分層圖。
> 可信度順序仍然是 **程式碼 > 緊鄰常數的註解 > 這份文件**。這裡的敘述反映撰寫當下的事實；`tools/knowledge_links.py` 只保證章節還在，**不保證內容還對**。

---

## 為什麼機構資料集中在一張表

`BANK_PROFILES` 之前是五張各自獨立的表（`BANKS`、`BANK_NAME_ALIASES`、`SUMMARY_CODE_OVERRIDES`、`SUMMARY_CODE_OVERRIDES_FINSUM`、`COMPOSITE_TERMS`）外加 `earningsCalls` 的 `PRIMARY_BANK_ENTITIES`——**加一家機構要改六個地方，而且沒有任何東西檢查六個都改了**。

漏改的下場不是報錯：少一筆 `composites` 只會讓某一家的輸出多出一列 N/A，跟「這家真的沒揭露」完全無法分辨。

現在那六個名字全部還在，只是改成從 profiles 推導出來的視圖；`_validate_profiles()` 在 import 時就擋下不完整的 profile，把執行期的靜默 N/A 變成啟動期的錯誤。

## profile 的六個欄位

### industries

這家的財報寫在哪些準則下。**這是讓機構軸能安全開放的關鍵。**

別名必須是短名（法說會封面寫「玉山金控」，不會寫登記全名），而短名在同一個集團內會互撞：「國泰人壽保險股份有限公司」包含「國泰」，所以壽險的財報曾被解析成它的兄弟**銀行**，並套用了那家銀行的 overrides 與 composites。

把偵測範圍限縮到財報自己的產業，是用結構消除這個問題，而不是祈禱別名永遠不撞。銀行與金控兩種準則對每家都列，是因為兩種文件都在範圍內。

### aliases

全名／別名。兩個用途：把使用者輸入的 `--bank 台北富邦銀行` 正規化成 `北富銀`，以及在沒給 `--bank` 時從財報自己的文字偵測機構。「臺」「台」都要列，兩種寫法都出現過。

**別名不能是日常用語。**「第一」單獨當別名會命中每一家財報裡的「第一季」「第一階段」，使 `第一銀行` 在**所有**資料夾都成為候選，`detect_bank` 因歧義而全部拒絕——症狀是整批資料夾被靜默跳過，不是報錯。所以只收 `第一商業銀行` / `第一銀行` / `第一金`。

### primary_entities

每份法說會簡報**主體銀行**的名稱。

金控的簡報會同時報告其他子行（富邦華一銀行用人民幣、富邦銀行(香港)用港幣…），而這些表的列標籤一模一樣（存放比、總放款、營業費用）。`_BANK_LABEL_HINT` 分不出來，因為它們全都含「銀行」。

**抓錯子行比抓不到更糟。** 真實案例：一份富邦簡報產出了 存放比 72.17%、放款餘額 81,769——那是大陸子行人民幣表的數字，不是台北富邦銀行的。

英文／羅馬拼音要一起列，因為簡報附錄常用英文表頭（"E.SUN Bank's Income Statement"）。少了它，這種標題會命中 `_ENTITY_NAME_RE`（因為有 "Bank"）但命不中 primary alias，於是這家自己的附錄反而被當成別家的而拒絕。

### code_overrides / code_overrides_finsum

單一 `SUMMARY_LAYOUT` 代碼的每機構覆寫（代碼 → 替代代碼）。

兩者分開是因為**季度簡式揭露**（依「公開發行銀行財務報告編製準則」第三十二條）跟完整個體財報是不同文件，而且確認過用不同的代碼方案。114Q4 實測：

| 機構 | 簡式揭露的稅後淨利 | 處理 |
|---|---|---|
| 中信 | 完全不印代碼（只有標籤） | 已被 `SUMMARY_LABEL_FALLBACKS["64000"]` 涵蓋，不需覆寫 |
| 北富銀 | 直接印 64000 | 不需覆寫 |
| 國泰 | 印 61000 —— **不是**完整財報需要的 63000 | 需要獨立的 finsum 覆寫 |

### composites

這家在每個 composite 項目的組成代碼。**不要從別家複製。**

真實差異（114Q4 個體財報）：

| 機構 | 評價及已實現 | 其他非利息收益 |
|---|---|---|
| 國泰／中信／北富銀 | 49200, 49310, 49450, 49600 | 49700, 49750, 49800(+) |
| 玉山 | 49200, 49310, 49600 | 49700, 49750, 49899 |
| 兆豐 | 49200, **43100**, 49450, 49600 | 49700, 49750, 49800 |
| 台新／永豐 | 49200, 49310, 49450, 49600 | 49700, 49750, 49800 |
| 新光 | 49200, 49310, 49600 | 49700, **49815**, 49899 |
| 第一 | 49200, **43100**, **43600**, 49600 | **45000**, 49750, 49800 |
| 華南 | 49200, 49310, 49450, 49600 | 49700, **47003**, 49899 |

兆豐與第一用 `43100` 而非 `49310`；第一另外用 `43600`（除列按攤銷後成本）與 `45000`（資產減損迴轉）；華南的權益法認列是 `47003`；新光整份沒有「除列按攤銷後成本」這一列。**抄別家會得到一個看起來完全正常的錯數字。**

## 代碼查不到時的三層退路

`SUMMARY_LAYOUT` 的代碼在真實財報裡不一定找得到。三層退路，順序固定：

### 一、標籤比對（SUMMARY_LABEL_FALLBACKS）

有些財報的轉檔會讓**那一列自己的代碼格是空的**（中信個體財報實測：小計／合計列根本沒有代碼），或真正的代碼跟 `SUMMARY_CODE_OVERRIDES` 假設的不同（國泰個體財報實測：「本期淨利」在 61000，不是覆寫表所依據的金控合併口徑 63000/64000）。

兩者其實是同一個問題：**對這些小計／合計列而言代碼不可靠，但標籤文字可靠**——這些列在觀察過的所有財報裡只用一小組固定措辭。

因此這張表用 `SUMMARY_LAYOUT`／覆寫後的代碼欄位當 key（也就是實際傳給 `find_code_value` 的值），而不是用某份財報碰巧使用的字面代碼。

比對是**整格精確相等**，不是子字串——這些都是短的獨立小計標籤（如「淨收益」），不會是別的複合科目名的子字串。第一銀行寫「淨收益合計」，同一列、同一個位置，只是多了合計後綴，所以別名要明列。

### 二、由組成項重建（SUMMARY_CODE_DERIVATIONS）

代碼與標籤都失敗後的最後手段。只用於**財報可以合法完全省略**的列。

兆豐與第一的 114Q4 個體財報把「營業費用」印成沒有金額的**區段標題**，接著三個明細列，然後直接跳到稅前淨利。沒有任何一列可以比對，代碼或標籤都不行。

**這是算術，不是猜測，而且事前雙向驗證過：**

- 有印 58400 的四家（台新／新光／永豐／華南），三項相加**分毫不差**等於印出來的合計
- 沒印的兩家，補出來的數字讓該財報自己的 `淨收益 − 呆帳 − 營業費用 = 稅前淨利` **差額為 0**（兆豐 28,951,175；第一 28,843,814）

補出來的列在 `note` 裡標明是 derived。**財報自己沒說的數字，不可以跟它說了的數字長得一樣。**

已知上限：若某份財報出現**第四個**營業費用組成項，這裡會靜默低估——這正是 note 要列出實際加總了哪幾項的原因。

### 三、放棄，並說明原因

三層都失敗就是 N/A，而且 `note` 會寫明是哪一種失敗。詳見 [N/A 的六種成因](#na-的六種成因)。

## N/A 的六種成因

N/A 不是一種狀況。每一種的修法不同，所以每一列 N/A 都在 `note` 裡標明是哪一種（同一個字串也會在 `-v` 印到主控台）。

| note 開頭 | 意思 | 修法 |
|---|---|---|
| `code XXXXX (X) not found in any file` | 這家用了別的代碼 | 確認財報裡真的沒有，再加 `code_overrides` |
| `'X' - none of [...] found in any file` | 標籤比對沒命中 | 加別名到該項的 `label_aliases` |
| `'X' has no formula defined for bank 'Y'` | 這家沒有該 composite 的公式 | 逆推組成代碼後補進 `composites` |
| `'X': component code Z not found` | composite 缺一個零件 | 同第一列 |
| `CIR needs 淨收益 and 營業費用...` | 上游兩列自己就是 N/A | 先修上游 |
| `no ROA/ROE: filing discloses no 獲利能力...` | 三個來源全空 | 見 [ROA/ROE 的三個來源](#roaroe-的三個來源) |

**活存比對目前所有機構都是 N/A，而且那是正確結果。** 十家的財報裡只有「活期存款」的餘額列，沒有任何揭露的比率。按紅線第五條，不代算。

超過一半的列是 N/A 時 `summary_coverage_warning` 會發出警告——那代表整份版面讀錯（產業判錯／機構判錯），不是缺揭露。

## SUMMARY_LAYOUT 為什麼綁死產業

這份 layout 的代碼是**直接對文件生比對**的，summary 模式從不載入產業科目字典，所以代碼本身不帶產業資訊。**同一個數字在不同準則下是不同科目**：`58200` 在金融業是呆帳提存，在保險業是保險成本。

把 layout 套到它不是為之而建的財報上**不會失敗**——它會把一個真實、解析正確的數字貼上錯誤的標籤。國泰人壽的財報實測：產業正確判為保險業，然後「保險成本」被以標準化 term「呆帳提存(收回)」輸出，正負號還被 `apply_cost_sign` 翻了。`matched_label` 仍然是「保險成本」，但 `term` 才是 CSV/Excel 匯出與 `_MERGED_TERM_ORDER` 使用的欄位，而標準化 term 正是這份 layout 存在的目的。

**所以沒有 layout 的產業一律拒絕，不預設。**

## ROA/ROE 的三個來源

優先順序固定：

1. **財報自己揭露的獲利能力表**——**照揭露值使用，不再年化**。早期版本一律用 `x4/季數` 縮放，假設台灣的銀行一致地在這裡報未年化的累計數。三家銀行各兩期的交叉比對推翻了這個假設：中信與玉山的 Q1 揭露值跟自己的 Q4 大致同量級（已年化），國泰的 Q1 大約是 Q4 的四分之一（確實未年化）——**慣例並不一致**，盲目縮放對其中一部分必然是錯的。
2. **法說會簡報自己報的數字**——由呼叫端（`userInteractions.cli`）提供，不是在這裡查，因為財報側不能 import 法說會側（會循環）。
3. **本財報的手算公式**（`compute_ratios`），明確標示為近似值。

不論哪個來源勝出，手算公式**都會**另外算一次當交叉核對值，**永遠不用它靜默覆蓋**揭露值；兩者背離超過門檻時在 `note` 說明。那個差距本身就是有用的訊號，不是該藏起來的東西。

### 手算公式為什麼要先除以季數

`net_income` 是**年初至今的累計數**，不是單季數——直接從財報自己的損益表欄位標題確認：Q4／年報的欄位寫「114年度金額」（**全年**），Q2 的欄位寫「一月一日至六月三十日」（上半年**累計**，不是單獨的 Q2）。

早期版本假設相反（單季），然後一律 `x4`。對 Q4 財報（本來就是全年）這會把已經年化的數字再乘四倍——三家銀行的 Q4 交叉核對出現約 4 倍偏高，就是這個原因。先除以季數在 `quarter_num=4` 時正確地退化成無操作，其他季則把部分年度的累計數投射成全年。

### 合理範圍為什麼開得那麼寬

`_ROA_PLAUSIBLE` = [-5, 5]%、`_ROE_PLAUSIBLE` = [-50, 50]%。**刻意寬**：虧損季是完全正常的輸入。所以這個檢查在真實資料上幾乎不該觸發——真的觸發了，那非常可能是解析錯誤（代碼錯、期別欄位錯、% 號誤讀），而不是某家銀行真的是離群值。

背離檢查比較的是**量級**，而且正負號相反直接判定背離。分子原本是 `max(value, crosscheck)` 且沒有 `abs()`，於是虧損季可能算出 1.0 甚至負的比值而靜默通過：`max(-3.0, 1.0)` 是 1.0。正負號相反代表一邊說賺一邊說賠，那是最大的分歧，卻從來沒被報出來過。

## 為什麼 summary 與 ratios 拆不開

`compute_ratios` 需要 `SUMMARY_CODE_OVERRIDES` 與 `SUMMARY_LABEL_FALLBACKS`；`collect_summary_rows` 需要 `collect_roa_roe`。兩邊互相依賴，所以不可能只切兩塊——機構／代碼宣告下沉成 `entities`，才讓分層變成無環：

```
statements → summary → ratios → profitability → entities → core
```

`_validate_profiles` 留在 `summary` 而不是跟資料一起放 `entities`，因為它是 **profiles × layouts 的交叉檢查**；放到資料那邊會把它存在的理由（那個環）又造出來。
